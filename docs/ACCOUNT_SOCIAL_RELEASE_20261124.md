# Account and social release handoff for Veylo

Prepared 2026-11-24 for [release candidate PR #43](https://github.com/andrewdiisso4/scenelink-api/pull/43), stacked on the earlier release audit in PR #42. **Integrated CI verification is still pending.** This describes reviewed source changes. The verification record below separates code/browser evidence from the remaining deployed-provider and signed-device gates. No production accounts, provider credentials, real email delivery, or signed iPhone build were exercised by this document.

**Conversation deletion is included in the candidate.** Direct threads with a deleted peer become unavailable and disappear from the inbox; the browser clears cached identity, messages, and editing state and rejects older in-flight responses. Existing groups remain usable and remove the departed author's cached messages using the current participant snapshot. A missing individual message is distinguished from lost conversation access, including a read receipt racing account deletion. Surviving authors' database messages are preserved. See [canonical message routes](../src/launch/messages.js), [message UI](../web/frontend/js/sl-social-messages.js), [actual-route regression](../qa/deleted-conversation.test.cjs), and [message DOM regressions](../web/frontend-tests/social-messages.test.cjs).

The browser review also exposed and corrected delayed signup autofocus that could move typing into the wrong field, old bundled CSS overriding login geometry/error contrast, and stale pending-request notices after an accepted friendship was refreshed. Mobile profiles now use the available card width for bio/actions, reduce unused space below the header, and keep all three section tabs visible together. Account controls mount after the asynchronous own-profile render inside Privacy & settings, survive saves without taking focus from an open deletion dialog, and are absent on another member's profile. The verification prompt follows the shared header and reserves its measured overlap on desktop.

## Backend-first rollout

1. **Freeze the integrated commit.** Capture its backend/frontend build identifiers and a reviewed database backup/restore receipt. Use the [native restore rehearsal](../qa/NATIVE_RESTORE_REHEARSAL.md) and existing release process.
2. **Upgrade the backend schema before exposing the new client.** The default [SQL loader](../src/server.js) selects migrations 002–014, 016, and 018 across the two migration directories. [Startup admission](../src/launch/bootstrap.js) requires the existing 007, 008, 009, 010, 012, 013, 014, and 016 markers plus `account-deletion-receipts-2026-11-24` from 018. Migration 018 only relaxes the old receipt email-hash constraint; it preserves historical values. A missing marker or migration failure must stop startup. Do not enable `RUN_ALL_SQL_MIGRATIONS` to bypass review: 017 is a separate venue-review migration outside this default rollout. The package's `migrate` command starts the server, not a standalone migration runner.
3. **Verify the upgraded API, then publish matching frontend assets.** Check the deployed source identifier, API contract, deletion requirements, and media capability against the intended environment. Build bundles, integrity metadata, and cache revision together from the final source. A frontend-only update cannot supply the new confirmation or receipt contract.
4. **Run the integrated checks and acceptance below.** The [release workflow](../.github/workflows/connected-release.yml) defines backend/frontend regressions, native PostgreSQL suites, analytics concurrency, and the [real Chromium account journey](../qa/account-browser-native.cjs). Keep the browser fixture on its guarded, empty loopback database. It blocks external providers; its screenshots cannot establish Google, Apple, SMTP, Cloudinary, or native iOS readiness.
5. **Complete provider and signed-device gates before submission.** Keep incomplete capabilities explicitly unavailable. Local account removal does not establish destruction of hosted photos, Apple revocation, or backup expiry. Use the [provider cleanup plan](account-deletion-provider-cleanup.md) for durable jobs, trusted ownership, legacy reconciliation, retry behavior, and honest completion wording.

## Manual acceptance with two disposable accounts

Use an authorized staging environment, two separate browser/device sessions, controlled mailboxes, fictional content, and test-owned photos. Account **A** uses email/password; **B** uses a provider without a SceneLink password. Repeat the run with Google and Apple separately. Record build IDs and sanitized observations; keep passwords, tokens, authorization codes, and private provider responses out of evidence.

| Step | Actions and required observations |
| --- | --- |
| 1. Signup and welcome | Create A. Confirm one welcome job and actual inbox receipt; inspect mobile/desktop HTML, blocked-image fallback, plain text, reply-to, and destination links. Logging in again must not enqueue another welcome. Before verification, participation is restricted but privacy controls, reporting, blocking, and account deletion remain available. Request the separate verification email, confirm it, then sign in again. A reused link fails. Missing SMTP must remain an explicit unavailable state. |
| 2. Profile persistence | Edit A's name, username, bio, city/neighborhood, and allowed social links. Save, reload, sign out/in, and compare every field. Clear a link and verify removal. In two A tabs, create a revision conflict: the stale tab must preserve its draft and offer reload, without claiming success. Cancel/reopen and keyboard focus must behave predictably. |
| 3. Photo behavior | With uploads unavailable, verify the explanatory state and retry control; text editing must still work. With authorized storage configured, upload a test-owned photo, confirm persisted readback, then remove and reload. Confirm selection/draft retention on injected failures and the absence of false success. For B, later provider sign-ins must preserve the chosen or removed photo. External deletion requires its separate cleanup evidence. |
| 4. Search privacy | Set B private and discoverable. From A, a partial name must not disclose B; exact username may return the limited profile. Disable B's discovery and confirm no nonfriend search result. Restore discovery for the next step. Verify loading, no-results, network failure, and sign-out do not show stale private results. |
| 5. Friendship and messages | A requests B; check outgoing versus incoming states. A cannot accept its own request. B accepts; reload both and confirm friendship. Set B's messaging to No one: Message actions disappear and direct sends fail. Restore Accepted friends, exchange fictional messages, and check privacy changes in an already-open conversation. |
| 6. Withdrawal and block | Remove the friendship and confirm shared access is withdrawn. Send another request, decline it as recipient, and verify the 24-hour retry restriction. Cancel an outgoing request in a fresh run if needed. Block/unblock and verify search, profile, and messaging restrictions; unblock must not silently restore friendship. To prepare the deletion case without waiting for the decline cooldown, explicitly allow Everyone messaging and reopen the existing direct thread after unblocking. |
| 7. Recovery and session isolation | Exercise A's forgotten-password email, valid reset, invalid/expired/reused links, matching password confirmation, and visibility controls. Verify old sessions stop working after reset. Check cross-tab logout, provider popup cancellation, unavailable providers, and late responses after switching accounts. Repeat keyboard and VoiceOver navigation on the signed device build. |
| 8. Reporting | Report fictional test content through the real UI. The moderation owner must confirm receipt and a review/action path; a success toast alone is insufficient. Check published support contact and privacy links from the app and welcome mail. |
| 9. Delete A while B watches | Leave B's direct thread with A open. In A's settings, test wrong password, then confirm permanent deletion. Require server confirmation before the success screen. Verify A cannot authenticate, B remains intact, and the minimal receipt exists using authorized test-database inspection. B's next sync must make the direct thread unavailable and remove departed-user cached content; list refresh must omit it. Also repeat in a group: surviving members retain access and their own stored messages, while cached departed-author content disappears. The dedicated route and DOM regressions cover these cases; the hosted/device run remains required. |
| 10. Delete B | Verify expired provider proof requests a fresh provider sign-in; then reopen deletion within five minutes and type DELETE. No invented password is required for a provider-only account. For Apple, confirm the manual revocation notice appears before deletion and remains accessible afterward. Follow the manual instructions, while keeping automatic revocation and historical-link coverage recorded as unfinished. Verify B's sessions and local data are removed. |

Use controlled fault fixtures for deletion rollback, missing receipt migration, upload/delete overlap, analytics concurrency, and unknown network outcomes. Do not create production failures to reproduce them. A deletion timeout means the result needs checking; it is neither confirmed success nor proof the account survived.
