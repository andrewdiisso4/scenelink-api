# Isolated SceneLink acceptance host

This launcher serves the combined repository's frontend and real Express API from one gated origin. It is an acceptance environment with a separate PostgreSQL database and fictional fixtures. It does not deploy, import, activate or modify production.

Start with `node qa/acceptance/start.cjs`. The accompanying `render.yaml` and `DEPLOYMENT_PROPOSAL.md` describe the proposed hosted resources; creating those resources remains a separate action.

## Required configuration

| Variable | Required value |
| --- | --- |
| `ACCEPTANCE_MODE` | `isolated-synthetic` |
| `ACCEPTANCE_ENVIRONMENT_ID` | `scenelink-release-qa-20261123` |
| `ACCEPTANCE_DB_NAME` | The database resource's actual database name: `scenelink_release_qa_20261123`, optionally followed by `_` and 1–16 lowercase letters/digits generated by the provider |
| `ACCEPTANCE_DB_HOST` | The dedicated database resource's actual hostname |
| `DATABASE_URL` | That same database's connection string; the host and path must match the two variables above exactly; query strings/fragments are rejected |
| `JWT_SECRET` | Independently generated secret of at least 32 bytes |
| `ACCEPTANCE_ACCESS_SECRET` | Independently generated secret of at least 32 bytes, used only for the outer gate |
| `ACCEPTANCE_FIXTURE_PASSWORD` | A separate generated password of 20–72 UTF-8 bytes, used to create the fictional accounts |
| `NODE_ENV` | `production` on Render; `test` only for local native smoke |
| `PORT` | The service's listening port; defaults to `10000` |

Hosted startup also requires Render's `RENDER_SERVICE_NAME`, `RENDER_EXTERNAL_URL` and full `RENDER_GIT_COMMIT`. The service name and HTTPS hostname must begin with `scenelink-release-qa-20261123`, with an optional generated dash suffix. No production SceneLink hostname is accepted. `.env` files are rejected before application configuration loads.

Local smoke uses an explicit literal-loopback PostgreSQL host and port, the same QA database name rule, and `ACCEPTANCE_PUBLIC_ORIGIN=http://127.0.0.1:<port>` (or IPv6 loopback). A non-production runtime cannot target a remote database.

Never commit or paste the three generated credential values into this document, test evidence, issues or PR comments. Retrieve them through the authorized service's environment controls when performing the approved acceptance run.

## Access and test accounts

An unauthenticated `GET /__acceptance/health` returns only `{status:"ok"}` after a successful bounded database probe, or a redacted `503` result. All other product pages, files and API requests require the outer gate cookie.

Open `/__acceptance/unlock` and enter the generated acceptance access secret. This sets a signed, four-hour `__Host-sl_acceptance` cookie with `HttpOnly`, `Secure`, `SameSite=Strict` and root scope. The cookie is separate from normal consumer/business bearer authentication: unlocking the environment does not grant an application role. `/__acceptance/` lists the fixture roles and paths without disclosing passwords. Locking clears the browser's gate cookie; rotating the access secret invalidates all outstanding gate cookies.

| Role | Email | Expected behavior |
| --- | --- | --- |
| Admin | `qa.admin@example.invalid` | May enter the admin portal after normal account sign-in |
| Member | `qa.member@example.invalid` | Consumer access; must be denied the admin portal |
| Approved owner | `qa.owner@example.invalid` | Business access to QA Harbor Table and QA Nightcap, including venue switching |
| Pending owner | `qa.pending@example.invalid` | Business sign-in must remain forbidden pending review |

All four accounts initially use `ACCEPTANCE_FIXTURE_PASSWORD`. Four explicitly fictional venue rows support dinner/drinks planning and owner controls. Three are eligible for this private fixture directory; QA Pending Cafe remains inactive. No real venue record is imported or activated.

## Database initialization and restarts

The launcher acquires a PostgreSQL advisory startup lock before inspecting the database. A first boot requires an empty public schema. It writes a marker bound to the environment ID, database name and hostname, then runs the application's real default schema/migration path. Fixtures are inserted in one transaction, and the marker records their completion.

Subsequent starts require the exact marker binding and never reseed completed fixtures. Password changes, hours, plan edits, deleted fixtures and other test mutations persist across service restarts. Changing `ACCEPTANCE_FIXTURE_PASSWORD` alone does not reset existing passwords. No automatic deletion/reset operation is provided.

The startup process is not claimed to be atomic across every application migration. A failure may leave a marked partial QA schema; a matching restart may rerun the idempotent application initializer. A nonempty schema with no marker, a foreign marker, or a malformed marker fails closed before application initialization. Production data is never a source for this environment.

## Explicit acceptance boundaries

The launcher forces outbound mail, model/provider calls, seed jobs, imports, upload credentials, push-provider credentials and telemetry off. No welcome-mail worker or scheduled importer is started. Outbound server HTTP is fenced. Password-email and unsupported external/import operations return an explicit unavailable response rather than claiming delivery or completion. Real-model quality, real inbox delivery, OAuth, third-party maps, direct device uploads, production backup restoration and venue import/activation remain separate gates.

The outer CSP limits connections, assets and forms to this origin, disallows frames and workers, and sets pages to `no-store` with no referrer. Netlify `_redirects`, `_headers` and `netlify.toml` files are not executed or served. `/api` goes directly to this process's real Express app with its full path preserved.

Two deliberate **acceptance-only browser overlays** are served without editing canonical frontend files:

1. `/env.js` pins API settings to this origin and disables OAuth identifiers even after bundled configuration replaces them. It preserves same-origin credentials on `fetch` so clients that normally send only bearer tokens also retain the outer gate cookie. External fetches are rejected before transport.
2. Service-worker registration/caching is disabled; `/sw.js` also retires any prior worker/cache on this QA origin. Offline/install/cache-update behavior is therefore not accepted by this host.

An in-browser success here establishes the served candidate's behavior with these disclosed overlays. It does not establish production deployment, provider activation, physical iPhone behavior, App Store approval or launch readiness by itself.

## Verification

Run guard, access-cookie, same-origin and actual connected-client tests:

```sh
node --test qa/acceptance/runtime.test.cjs
```

For the native startup/restart smoke, first create a new empty local PostgreSQL database with the required QA name. Set its connection string through the environment, then run:

```sh
SCENELINK_ACCEPTANCE_NATIVE_SMOKE=yes node qa/acceptance/native-smoke.cjs
```

`ACCEPTANCE_SMOKE_DATABASE_URL` must name that literal-loopback database with an explicit port. The script generates credentials internally without printing them. It verifies refusal of a foreign nonempty schema, real gated static/API access, all four account boundaries, persistence across restart, secret-free status/logs and refusal of a foreign marker. It intentionally leaves its own isolated schema for the caller to dispose of; it refuses to start against existing tables.

The native script's scope is local HTTP and real PostgreSQL. A separate real-browser run must verify the Secure cookie, full bundled frontend state, actual click/keyboard flows and absence of production network traffic. Physical iPhone/Safari acceptance remains distinct from desktop Chromium.
